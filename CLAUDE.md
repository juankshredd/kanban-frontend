# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

This is the frontend for a Kanban dashboard app: Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS v4, and `@dnd-kit` for drag-and-drop. It is a standalone repo; a separate sibling repo at `../kanban-backend` (Express + a `db.js` data layer, JWT auth) provides the REST API this app talks to.

## Commands

```bash
npm run dev        # start dev server (http://localhost:3000)
npm run build      # production build
npm run start      # run the production build
npm run lint       # eslint (flat config via eslint.config.mjs)
npm test           # run the unit test suite once (vitest run)
npm run test:watch # run the unit test suite in watch mode (vitest)
```

## Testing policy

**Every new functional change (a new component, a new `lib/*` helper, a new prop/behavior on an existing component) must ship with unit tests covering at least one happy path and one negative/edge case — no exceptions.** This isn't optional polish; a PR/change that adds behavior without tests is incomplete. Purely presentational tweaks (e.g. a one-off className change with no new logic) don't need a new test, but if you touch a file that already has a `*.test.ts`/`*.test.tsx` sibling, keep it passing and extend it if the change adds a new branch.

Test tooling is [Vitest](https://vitest.dev) + `@testing-library/react`, configured in `vitest.config.ts` (jsdom environment, `@/*` alias matching `tsconfig.json`, setup file `vitest.setup.ts` which loads `@testing-library/jest-dom` matchers). Conventions:
- Test files live next to the code they test, named `<file>.test.ts` / `<file>.test.tsx` (e.g. `lib/taskHierarchy.ts` → `lib/taskHierarchy.test.ts`). This mirrors how `lib/taskType.ts`/`lib/taskDetails.ts` sit next to the components that use them — no separate `__tests__` tree.
- Pure functions in `lib/*` (no React) get plain Vitest unit tests — see `lib/taskHierarchy.test.ts` for the pattern (happy-path grouping/nesting cases, then a "Negative / edge cases" block for malformed input, missing data, cycles, etc.).
- Components get `@testing-library/react` `render()` tests — see `components/kanban/TaskCard.test.tsx` / `TaskCardTree.test.tsx`. Components using `@dnd-kit`'s `useSortable`/`useDroppable` render fine in tests without wrapping them in a real `DndContext` (those hooks have safe internal default contexts) — don't add a `DndContext` test wrapper unless a test specifically needs actual drag behavior.
- `lib/testFixtures.ts` exports `makeTask(overrides)`, a `Task` factory that fills every required field with a sane default and auto-increments `id`/`ticket_id` — use it instead of hand-rolling task objects in new tests, and extend it (rather than duplicating a fixture builder elsewhere) if a future type needs its own factory.

## Architecture

**API access**: All backend calls go through the single `api()` helper in `lib/api.ts`. It targets `process.env.NEXT_PUBLIC_API_URL` (falls back to `http://localhost:5000`), prefixes every call with `/api`, and attaches `Authorization: Bearer <token>` by reading the JWT from `localStorage.getItem("token")`. There is no other data-fetching layer (no React Query/SWR, no server actions) — pages call `api()` directly from client components. To point at a running backend, set `NEXT_PUBLIC_API_URL` in `.env.local`. On a non-2xx response it throws `ApiError` (also exported from `lib/api.ts`), which extends `Error` but also carries `status` (HTTP status code) and `data` (the parsed JSON error body) — use `err instanceof ApiError && err.status === 404` etc. when a page needs to branch on the specific error shape (e.g. distinguishing 404 "not found/no access" from a 409 conflict body) rather than string-matching `err.message`.

**Auth**: Login/register pages (`app/login`, `app/register`) call `/auth/login` and `/auth/register` and store the returned JWT in `localStorage` under the key `token`. There's no auth context/provider or route guard yet — none of the app's pages check for a token before rendering.

**Routing**: `app/page.tsx` immediately redirects to `/login`. Main routes: `/login`, `/register`, `/companies` (list), `/companies/[companyId]` (detail: edit, members, projects), `/projects` (all projects the user belongs to, across companies), `/projects/[projectId]` (redirects to `./board`), `/projects/[projectId]/board` (the kanban board), `/projects/[projectId]/members`. There is no `/dashboard` route — a single-project dashboard used to live at `app/dashboard/page.tsx` but was replaced by the per-project board under `/projects/[projectId]/board` when the app moved from "one implicit project" to multi-project (and then multi-company) support.

**Companies**: A company groups projects and has its own membership separate from project membership (`role: "OWNER" | "MEMBER"` per company, see `types/company.ts`). `POST /api/projects` requires a `company_id`, so project creation is only ever done in one place — embedded in the company detail page (`app/companies/[companyId]/page.tsx`), which posts to `POST /companies/:id/projects` via `CreateProjectModal` (its `companyId` prop is required, not optional — don't reintroduce a standalone "new project" form that posts to `/projects` directly). Being a company member does **not** imply access to every project in that company — `GET /companies/:id/projects` only returns projects the user is also a `project_member` of, so an empty list there is expected/normal, not a bug; the company detail page's copy reflects that explicitly rather than implying the company has no projects. Company-scoped endpoints 404 (not 403) when the user isn't a member, by backend design — treat that as "not found / no access", not a distinct error state.

**Project shell (sidebar)**: Every route under `app/projects/[projectId]/` is wrapped by `app/projects/[projectId]/layout.tsx`, a Jira-style persistent left menu (dark theme, matching the rest of the app — not the light Jira reference it was modeled on). The layout wraps `children` in `ProjectProvider` (`context/ProjectProvider.tsx`, same createContext+provider+hook-in-one-file shape as `ThemeProvider`) which does the *only* `GET /projects/:id` fetch for the whole project subtree and exposes `{ project, loading, notFound, error, refreshProject }` via `useProject()`. It renders `components/layout/ProjectSidebar.tsx` (project/company header, nav sections, collapse toggle) next to `children`, and short-circuits to a "not found / no access" screen when `useProject().notFound` is true (same 404-handling convention as the company detail page) — individual pages under `[projectId]/` don't need to fetch the project or handle that 404 themselves.
- **Adding a module to the sidebar**: create `app/projects/[projectId]/<module>/page.tsx`, then add one entry to `PROJECT_NAV_SECTIONS` in `lib/projectNav.tsx` (new item in an existing section, or a new section). That array is the sidebar's only data source — no other file changes. Today it only lists Board and Members, because those are the only modules with real backend support; don't add nav entries for pages that don't exist yet.
- Pages under `[projectId]/` (e.g. `board/page.tsx`, `members/page.tsx`) read project data via `useProject()` instead of fetching `GET /projects/:id` themselves, and call `refreshProject()` (not a local re-fetch) after a mutation that should update the header/member list.

**Kanban board** (`app/projects/[projectId]/board/page.tsx`): reads tasks via `GET /projects/:projectId/tasks` and derives the three columns (`TODO`, `IN_PROGRESS`, `DONE`) by filtering the flat `Task[]` on `Task.status` (see `types/task.ts`) rather than storing per-column state. The full unfiltered `tasks` array is also threaded down through `Column` as `allTasks` (a second, distinct prop from the per-column, status-filtered `tasks` prop `Column` already takes) so `CreateTaskModal`/`TaskDetailsModal` can compute parent-card candidates without a separate fetch — see "Card hierarchy" below. Drag-and-drop is wired with `@dnd-kit/core` + `@dnd-kit/sortable`:
- `Column` (`components/kanban/Column.tsx`) is a droppable zone whose `id` is the column's status string (`TODO` / `IN_PROGRESS` / `DONE`), takes the current `projectId` as a prop (needed to scope task creation), and wraps its tasks in a `SortableContext`. It renders `buildTaskTree(tasks)` through `TaskCardTree`, not a flat `tasks.map(...)` into `TaskCard` — see "Nested/contained child cards" below.
- `TaskCard` (`components/kanban/TaskCard.tsx`) is the sortable/draggable item, keyed by `task.id`. Its "Details" button opens `TaskDetailsModal` (`components/kanban/TaskDetailsModal.tsx`), which edits a task's per-type extra fields (`task.details`, see `lib/taskDetails.ts`) and, when the type supports one, its parent card — both saved in a single `PATCH /projects/:projectId/tasks/:id`.
- On `DragEnd`, the target column id becomes the task's new `status`; the UI updates optimistically before `PATCH /projects/:projectId/tasks/:id` fires, and re-fetches from the server on failure to roll back.
- Task creation happens through `CreateTaskModal` (opened from the `TODO` column only, scoped to `projectId`), calling `POST /projects/:projectId/tasks`.
- Task deletion is only exposed for `TODO` tasks (see the status check in `TaskCard`); deleting a task that has children (see hierarchy below) is rejected by the backend with a 409, surfaced via the board's existing `error` banner.

**Card hierarchy**: cards form a fixed containment chain `EPIC → FEATURE → STORY → TASK/BUG` via each task's `parent_id` (nullable, `types/task.ts`). The chain is defined client-side by `TASK_PARENT_TYPE` in `lib/taskType.ts` (`EPIC: null, FEATURE: "EPIC", STORY: "FEATURE", TASK: "STORY", BUG: "STORY"`) — this mirrors the same-named constant in `kanban-backend/src/controllers/taskController.js`, which is the source of truth and re-validates `parent_id` server-side on every create/update regardless of what the frontend sends. `getParentCandidates(tasks, childType)` (same file) filters an already-fetched task list down to the tasks of the one type a given child type is allowed to attach to — both `CreateTaskModal` and `TaskDetailsModal` call this against the `tasks`/`allTasks` list threaded down from the board page (no dedicated "list valid parents" endpoint or fetch). A type with no allowed parent (`EPIC`) renders no parent field at all; a type that allows one but has zero existing candidates renders a disabled hint instead of an empty `<select>`.

**Nested/contained child cards (board rendering)**: within a column, a child card renders visually nested inside its parent's card (smaller, indented, contained) instead of as an equal-sized sibling — this is purely a rendering concern layered on top of the hierarchy above and doesn't change how `parent_id` is stored or validated. Three pieces, each single-responsibility:
- `lib/taskHierarchy.ts` exports `buildTaskTree(columnTasks: Task[]): TaskNode[]` (`TaskNode = { task: Task; children: TaskNode[] }`), a pure function that groups **one column's already status-filtered task list** into a tree by `parent_id`. It only looks at `parent_id`, not `TASK_PARENT_TYPE`, so it's generic across the whole chain (not hardcoded to `STORY`/`TASK`). Critically, a task only nests under a parent that is **also present in that same `columnTasks` array** — since a `STORY` and its child `TASK` can have different `status` values (dragged independently between columns), a child whose parent lives in a different column has no parent card to nest inside, so it falls back to rendering as its own root/top-level node. The function is defensive against malformed `parent_id` data (self-reference, cycles) via a single-pass grouping — see `lib/taskHierarchy.test.ts` for the exact guarantees.
- `components/kanban/TaskCard.tsx` stays hierarchy-agnostic: it takes two optional props, `compact?: boolean` (shrinks paddings/text sizes and swaps `bg-slate-800` for a lighter `bg-slate-700` background) and `children?: React.ReactNode` (rendered in an indented, left-bordered slot beneath the card's own content, only when non-empty — an outer `border` is added when there's nested content, to read as a "container"). It has no knowledge of `parent_id`/`TaskNode`. Note `hasNestedContent` cannot be `Boolean(children)` — `Boolean([])` is `true` in JS, so an empty children array (a childless tree node) would otherwise always render the nested/bordered state; it must special-case `Array.isArray(children) ? children.length > 0 : Boolean(children)`.
- `components/kanban/TaskCardTree.tsx` is the thin recursive component that walks a `TaskNode` and composes `TaskCard`s, passing `compact={depth > 0}` and rendering `node.children` as nested `TaskCardTree`s inside the parent `TaskCard`'s `children` slot. `Column.tsx` calls `buildTaskTree(tasks).map(node => <TaskCardTree node={node} depth={0} .../>)` instead of mapping `tasks` directly into `TaskCard`s; `SortableContext`'s `items` list is unaffected (still every task id in the column, flat) since dnd-kit's sortable hooks don't require flat DOM structure.
- To extend nesting to another pair in the chain (e.g. visually nesting `STORY` inside `FEATURE`), no changes are needed here — `buildTaskTree` already builds the full multi-level tree from `parent_id` alone; it's already recursive by construction.

**`TaskDetailsModal` (Jira-style layout)**: `components/kanban/TaskDetailsModal.tsx` is a wide two-column modal (`grid-cols-[minmax(0,1fr)_372px]`, `w-[1240px] max-w-full`) modeled on a Jira ticket detail view — laid out and structured after a design handoff mockup, but using the app's existing slate/blue dark theme (not the mockup's own color tokens), and showing **only the sections a given card type actually has data for**: a leaf type (`TASK`/`BUG`) never renders "Child issues" (`getChildTypes(task.type).length === 0`); a type with no legal parent (`EPIC`) never renders `+ Add related card` (`canGainParent(task)` is false). Left column: title, action row, description (read-only display — the backend's `PATCH /tasks/:id` has never accepted `title`/`description`, so these were never editable here), the existing per-type `details` fields (unchanged), and `ChildIssuesList`. Right column: a status `<select>` (PATCHes `{ status }` immediately on change, refreshing without closing the modal — the first place in the app status changes outside board drag-and-drop), a "Details" box with the existing Parent `<select>`/`getParentCandidates` logic (unchanged, just relocated here) and the type tag, timestamps, and the existing `Cancel`/`Save` footer (still only persisting `details` + `parent_id`, exactly as before). The `parentId` external-resync `useEffect` (a previous code-review fix) still applies: `CreateRelatedTaskModal`, opened from this same modal, can update `task.parent_id` out from under it while it stays mounted.

**`CreateRelatedTaskModal` (parent-only)**: creates a new parent task and links the currently-open task under it — `POST .../tasks` with `type: TASK_PARENT_TYPE[sourceTask.type]` (never a choice; a card has exactly one legal parent type), then `PATCH .../tasks/:sourceTaskId` setting `parent_id` to the newly created task. Only ever mounted when `canGainParent(sourceTask)` (`lib/taskType.ts`) is true — it has no relation picker or child-creation branch (that used to exist here; see "Child issues" below for where child-creation moved). `pendingParentId` state remembers the created-but-not-yet-linked task across a failed `PATCH` *and* across `Back`-then-retry, so retrying only re-attempts the link instead of double-`POST`ing a duplicate orphan parent — both are regressions a previous code-review pass caught and fixed; preserve this behavior in any further changes here. Every `handleCreate` attempt calls `refresh()` exactly once in `finally`, regardless of outcome, so a create-succeeds-but-link-fails task still surfaces on the board instead of only appearing after a successful retry.

**Child issues (`components/kanban/ChildIssuesList.tsx`)**: the only "create a child task" entry point now (the header's `Create subtask` button just focuses this list's quick-add input via a `quickAddRef` passed down from `TaskDetailsModal`) — `CreateRelatedTaskModal` no longer has a child-creation path, avoiding two different UIs for the same action. `lib/taskHierarchy.ts` exports `getDirectChildren(tasks, parentId)` (unlike `buildTaskTree`, not scoped to one column — a task's children can be `DONE` in a different status than the parent and still need to show here) to compute the `childTasks` prop. Per row: a status `<select>` (immediate `PATCH { status }`), and a remove button that **unlinks** (`PATCH { parent_id: null }`) rather than deletes — a child can be any status, and the board's own delete button is `TODO`-only, so unlink is the safe, always-available action. Quick-add POSTs with `type: getChildTypes(parentTask.type)[0]` (defaults to the first legal child type, e.g. `TASK` for a `STORY`); if the user meant the other legal type (e.g. `BUG`), they fix it afterward via the type badge `<select>` already on that child's own `TaskCard` — no type picker in the quick-add row itself. Drag-reorder is native HTML5 DnD (not `@dnd-kit` — this list lives inside a modal overlay, a separate DOM subtree from the board's own `DndContext`, so there's no conflict), with live-splice-on-`dragover` visual feedback but the persisting `PATCH { after_task_id }` firing only on `drop`/`dragend`. This moves the child's *global* per-project `rank` (the same value the board's own columns sort by), which is an accepted, intentional side effect of reusing the existing single-rank-list model — not a bug to "fix" by giving children their own separate ordering.

**"Related to" (non-hierarchical link) is explicitly out of scope** — the backend's only relationship mechanism is the single `parent_id` column enforcing the strict `TASK_PARENT_TYPE` chain (confirmed against `kanban-backend/src/controllers/taskController.js` and its migrations: no junction table, no `related_to`/`blocks`/`depends_on` concept exists there). Adding it would need a new backend migration/table/endpoints (plus that repo's own mandatory per-controller tests and a separate PR into its protected `dev`) before any frontend work — don't build a "Related to" option against the current schema; it has nothing to persist to. Likewise, `Assignee`/`Reporter`/`Points`/`Labels`/`Sprint` display, the "Relationship map" card, and the "Development"/"Activity" sections from the original mockup were deliberately left out of `TaskDetailsModal` for the same reason (no backing columns/tables, or — for Development/Activity — no GitHub integration or comments system at all); don't add UI for them without adding the backend support first.

**Theming**: `context/ThemeProvider.tsx` implements dark mode by toggling the `dark` class on `<html>` (Tailwind's class-based dark mode) and persisting the choice to `localStorage` under `theme`, falling back to `prefers-color-scheme`. It intentionally renders children without the context during the first mount to avoid hydration mismatches — `useTheme()` returns a safe no-op default `{ isDark: false, toggleDarkMode: () => {} }` when called outside the provider (it does not throw). `Providers` (`app/providers.tsx`) wraps the whole app in `app/layout.tsx`. Both `ThemeProvider` and `ThemeToggle` derive their client-only "mounted" flag with `useSyncExternalStore(subscribeNoop, () => true, () => false)` rather than a `useState(false)` + `useEffect(() => setMounted(true), [])` pair — see the ESLint note below for why.

**Styling**: Tailwind utility classes are used throughout, plus a set of hand-written semantic classes in `app/globals.css` (`.kanban-column`, `.task-card`, `.task-title`, `.task-desc`, `.btn-primary`, etc.) with their own `html.dark ...` overrides. When touching kanban board or card visuals, check `globals.css` in addition to inline Tailwind classes — styling for those elements is split across both.

**Path alias**: `@/*` maps to the repo root (see `tsconfig.json`), e.g. `@/lib/api`, `@/components/kanban/Column`, `@/types/task`.

## Notes for changes

- `types/task.ts` (`TaskStatus = "TODO" | "IN_PROGRESS" | "DONE"`) is the single definition of task status and column identity — column titles, droppable ids, and the status filter logic in the board page all depend on these three literal strings matching exactly. `TaskType` (`"EPIC" | "FEATURE" | "STORY" | "TASK" | "BUG"`) is the equivalent single definition of card type — adding a type means updating `TASK_TYPES`/`TASK_TYPE_CONFIG` and `TASK_PARENT_TYPE` in `lib/taskType.ts` *and* `TASK_DETAIL_FIELDS` in `lib/taskDetails.ts` (a `Record<TaskType, ...>` in each fails to typecheck otherwise) *and* the backend's own copies of all three maps in `taskController.js` — there is no shared package between the two repos, so these are kept in sync by hand and by comments pointing at each other, not by import.
- `CreateTaskModal` takes `{ projectId, tasks, close, refresh }`; `TaskDetailsModal` takes `{ task, projectId, tasks, close, refresh }` — both need the full (unfiltered) project task list as `tasks` to compute parent-card candidates via `getParentCandidates`, not just the tasks relevant to the column/card they were opened from. `CreateRelatedTaskModal` takes `{ sourceTask, projectId, close, refresh }` (no `tasks` — it never needs a candidate list, since it only ever creates a brand-new parent). `ChildIssuesList` takes `{ parentTask, childTasks, projectId, refresh, quickAddRef? }` — its prop is `childTasks`, not `children`; ESLint's `react/no-children-prop` rejects passing a plain value as a prop literally named `children` (it's reserved for JSX nesting), so any future "list of X" prop on a non-children-taking component needs a name other than `children` too. `CreateProjectModal` takes `{ companyId, close, onCreated }` (posts to `/companies/:companyId/projects`, not `/projects`) — check the current prop shape in `Column.tsx` / the company detail page before wiring any of these up elsewhere.
- **ESLint `react-hooks/set-state-in-effect`** (from `eslint-config-next`'s React Compiler-powered `eslint-plugin-react-hooks`) flags `useEffect(() => { ...; setSomeState(x); }, [])`-shaped effects — including indirectly, through a call to a component-scope function whose body ends in a `setState` call — as an error, not just a warning, and CI (`npm run lint`) fails the build on it. It over-fires on legitimate one-time "read an external source and sync it into state" effects (e.g. reading `localStorage`/`matchMedia` on mount), which is exactly what React's own docs describe as a valid effect. Two ways this repo resolves it, in order of preference:
  1. If the state is a simple client/server mount flag, use `useSyncExternalStore(subscribeNoop, () => true, () => false)` instead of `useState` + effect (see `ThemeProvider.tsx` / `ThemeToggle.tsx`) — this sidesteps the rule entirely because there's no effect-time `setState` at all.
  2. Otherwise (e.g. syncing from `localStorage` into real component state, as in `ThemeProvider`'s theme-restore effect, or a plain "fetch a list on mount" effect as in `app/companies/page.tsx`), add a narrowly-scoped `// eslint-disable-next-line react-hooks/set-state-in-effect -- <why>` directly above the flagged call rather than restructuring the whole component around the linter.
- **`react-hooks/immutability`** also flags a component-scope `const fn = () => {...}` referenced by an earlier-declared `useEffect` purely due to source order (even though it works fine at runtime, since the effect only runs after render). Fix by hoisting the function — either move its `const` declaration above the effect, or, if it doesn't close over component state/props, pull it out of the component entirely as a plain top-level function declaration (preferred, since top-level `function` declarations are hoisted and it avoids a pointless per-render redefinition).
